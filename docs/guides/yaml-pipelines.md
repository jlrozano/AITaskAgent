# Declarative pipelines in YAML

A pipeline can be written in YAML instead of C#. The engine reads the files, compiles the JSON
Schemas into **real C# types** with Roslyn at startup, wires the steps into a graph, and validates
the whole thing before anything runs.

The compiled-types part is the design decision that matters. The obvious way to build a dynamic
pipeline is to pass `JObject` around and inspect it at runtime; this engine deliberately does not,
so the execution machinery, the telemetry and the observability tooling see the same strongly typed
results whether a step was written in C# or declared in YAML.

Each schema becomes two types: a `{Name}Data` POCO generated by NJsonSchema, and a
`{Name} : LlmStepResult<{Name}Data>` wrapper that is what actually flows through the pipeline.
That wrapper is why nothing downstream needs a special path for declarative steps.

## A pipeline file

```yaml
name: DocumentProcessingPipeline
steps:
  - !LlmStep
    stepId: step_1_classify
    inputSchema: DocumentInput
    outputSchema: ClassificationOutput
    profileName: default
    useConversationHistory: false
    systemPrompt: "@[prompts/classifier.md]"
    userPrompt: |
      Document content: {{input.content}}
      Classify the document and return the original content in the `content` field.
    dependsOn: []

  - !LlmStep
    stepId: step_2_extract
    inputSchema: ClassificationOutput
    outputSchema: ExtractionOutput
    profileName: default
    systemPrompt: "@[prompts/extractor.md]"
    userPrompt: |
      Document type: {{input.type}}
      Extract the relevant key fields.
    dependsOn: [step_1_classify]
```

`!LlmStep` is a YAML **tag**, not a `type:` property. Tags are registered by reflection over the
types of every loaded assembly that carry `[YamlStepTag]` and implement `IYamlStep`, and each step
is instantiated with `ActivatorUtilities` (constructor dependencies come from DI), so adding a new
step kind means writing the class — no change to the parser and no registration of the step itself.

| Key | Meaning |
|---|---|
| `stepId` | Unique name; other steps address it in `dependsOn` |
| `inputSchema` / `outputSchema` | Names of JSON Schema files, compiled to real types |
| `profileName` | Which LLM role to run with; omit to use the environment's `DefaultRole` |
| `systemPrompt` / `userPrompt` | Prompt text, resolved as described in [Prompt templates](#prompt-templates). Without `systemPrompt`, the role's `SystemPrompt` is used; without `userPrompt`, the input is sent serialized as JSON |
| `useConversationHistory` | `false` starts the step with a clean conversation (default `true`) |
| `dependsOn` | Graph edges |

Both `inputSchema` and `outputSchema` are required. A step missing either is rejected at build time.

## Schemas

One JSON Schema file per type. The name you reference in `inputSchema` / `outputSchema` is the
**file name without extension** (`schemas/ClassificationOutput.json` → `ClassificationOutput`);
`title` is not used for naming:

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "type": "object",
  "title": "ClassificationOutput",
  "properties": {
    "content":    { "type": "string" },
    "type":       { "type": "string" },
    "confidence": { "type": "number" }
  },
  "required": ["content", "type", "confidence"]
}
```

`SchemaCompiler` generates a POCO named `{Name}Data` and a wrapper
`{Name} : LlmStepResult<{Name}Data>`, compiles them in memory with Roslyn and loads the assembly.
That wrapper is what flows through the pipeline as an ordinary `IStepResult`.

### JavaScript validation

A compiled type can carry a `validate(self, context)` function, executed with ClearScript V8 after
the LLM responds. It is not read from the schema file: pass it as the `jsValidateFunction` argument
of `SchemaCompiler.CompileAsync(name, jsonSchema, jsValidateFunction)` (`CompileFromFolderAsync`
never supplies one). It receives the whole `PipelineContext`, so a field can be validated against
what an earlier step produced — the kind of cross-step rule that cannot be expressed in JSON Schema
alone. It must return a boolean; `false` fails the result's structural validation, which
`RetryMiddleware` turns into a retry (with no error text: the generated `ValidateAsync` returns a
`null` message).

## Building and running

`AddAITaskAgent()` does not register the YAML engine; register it yourself and compile the schemas
before building the pipeline (the factory looks the types up with `SchemaCompiler.GetCompiledType`,
which throws for a schema that was never compiled):

```csharp
services.AddSingleton<SchemaCompiler>();
services.AddSingleton<YamlPipelineFactory>();
// ...
var compiler = provider.GetRequiredService<SchemaCompiler>();
await compiler.CompileFromFolderAsync("schemas");

var factory = provider.GetRequiredService<YamlPipelineFactory>();
var yamlPipeline = await factory.CreateFromFolderAsync("pipelines");

var result = await yamlPipeline.ExecuteAsync(input, cancellationToken: ct);
```

The input must already be an instance of the first step's compiled input type (or something the
pipeline can wrap into it).

All `*.yaml` files under the folder tree are concatenated, separated by `---`, before
deserializing (`CreateFromYaml` accepts the text directly).

## Failing before it runs

The factory refuses to build a pipeline it knows is wrong, rather than discovering it three LLM
calls in:

- **Unknown dependency** — a `dependsOn` naming a step that does not exist.
- **Cycles** — detected by topological sort.
- **Schema mismatch** — a step's `inputSchema` must equal the `outputSchema` of the step it depends
  on. Two steps that disagree about the shape of their data never start.
- **Unknown role** — `profileName` must name a role in the configured `LlmEnvironment`; the error
  lists the roles that do exist.
- **Missing schema** — a step without `inputSchema` or `outputSchema`.

## No secrets in YAML

A step names a role, never a key or an endpoint. Credentials live in configuration and are resolved
through `LlmEnvironment`, so a pipeline file is safe to commit and to share between environments.
See [Configuration](configuration.md).

## Prompt templates

Both prompts go through `PromptTemplateResolver`, the same resolver `TemplateLlmStep` uses, with
the model `{ Input = input.Value, Context = context.Metadata }`:

- **No `ITemplateProvider` in DI**: the text is rendered inline by `TinyTemplateRendered`, so
  `{{input.content}}`, `{{context.somekey}}` and `@[relative/path.md]` includes (resolved against
  the working directory) work.
- **An `ITemplateProvider` in DI**: the whole value is passed to `ITemplateProvider.Render` as a
  template **name** (with `FileTemplateProvider`, `<folder>/<value>.md`; there is no special `@`
  prefix). If no template has that name, the text is returned **unrendered**, placeholders
  included.

There is no `inputData` variable: a `{{inputData.x}}` placeholder renders empty.

## Current limits

- Generated assemblies are recompiled on every start; there is no on-disk cache keyed by schema
  hash.
- Each JavaScript validation creates its own V8 engine, with no pooling.
