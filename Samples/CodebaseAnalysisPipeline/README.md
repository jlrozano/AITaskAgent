# Codebase Analysis Pipeline

Pipeline de AITaskAgent que audita un repositorio a partir de un grafo de conocimiento en SQLite y genera nueve informes técnicos especializados más un resumen ejecutivo, todos en Markdown. El grafo lo construye `codebase-memory-mcp` para el código fuente y OfficeTools para los artefactos de Microsoft Access (`.accdb`, `.mdb`) y Word (`.docx`). Los auditores son agentes LLM que reciben los datos del grafo ya extraídos por SQL y que pueden, además, leer el código con herramientas.

El pipeline no está atado a un lenguaje: las plantillas exigen adaptar el criterio al ecosistema detectado y prohíben penalizar a un lenguaje por no usar herramientas que no forman parte de su plataforma. La calidad de los datos sí depende del lenguaje, porque cada indexador etiqueta cosas distintas (véase el apartado 7).

El código está repartido en tres proyectos. `Samples/CodebaseAnalysis.Core/` es una librería con el pipeline (steps, tools, modelos, plantillas y configuración), lo que hace falta para alojarlo (carga de configuración, construcción de roles LLM, resolución de argumentos y ejecución), la traducción de los eventos del framework a eventos de progreso y el agente de chat. `Samples/CodebaseAnalysisPipeline/` es la CLI: solo `Program.cs`, que configura el log, conecta opcionalmente con MCP, llama a la librería e imprime el resumen final. `Samples/CodebaseAnalysisWeb/` es una aplicación web local que ejecuta el mismo pipeline con progreso en vivo, visor de informes y un chat sobre el repositorio analizado; su uso y su API están en [su README](../CodebaseAnalysisWeb/README.md). Los tests están en `Samples/CodebaseAnalysis.Core.Tests/` y `Samples/CodebaseAnalysisWeb.Tests/`.

## 1. Requisitos

- **.NET 10:** el proyecto compila contra `net10.0`.
- **codebase-memory-mcp:** necesario cuando hay que indexar, es decir, si la BD no existe, si se fuerza la reindexación o si la BD no contiene nodos estructurales. Se busca, por este orden, en `McpServers:CodebaseMemory:Command`, `CodebaseMemory:CliPath`, `%LOCALAPPDATA%\Programs\codebase-memory-mcp\codebase-memory-mcp.exe` y el `PATH`. Sin él, el paso 1 aborta con un error explícito.
- **Microsoft Access (COM):** solo para repositorios con `.accdb`/`.mdb`; el extractor de OfficeTools exporta el VBA y los formularios a través de Access.
- **BdpGraphEnricher.CLI (opcional):** enriquecedor Roslyn para soluciones .NET. Sin él se usa el enriquecimiento por LLM (paso 2).
- **JDK 17 o superior (opcional, repositorios Java):** lo usa el analizador Java del apartado 3.2. La aplicación no lo instala ni lo descarga: basta un JDK descomprimido cuya carpeta se indica en `JavaAnalyzer:JdkPath`. Sin él, el análisis sigue con el grafo de `codebase-memory-mcp` y un aviso.
- **Proveedor LLM:** cada entrada de `LlmConfiguration:Providers` es un servicio `azure-openai`, `openai` u `openrouter`. En Azure, la clave se toma de `Asistente:ApiKey` o de la variable de entorno `Asistente__ApiKey` (proceso, usuario o máquina) y, si no existen, de la `ApiKey` del proveedor. Si un proveedor no tiene clave, el programa lo avisa al arrancar.

## 2. Ejecución

```powershell
dotnet build Samples/CodebaseAnalysisPipeline/Samples.CodebaseAnalysisPipeline.csproj

dotnet run --project Samples/CodebaseAnalysisPipeline/Samples.CodebaseAnalysisPipeline.csproj --no-build -- `
    --repo "C:\ruta\al\repositorio" --force-reindex true
```

Los argumentos de línea de comandos se imponen a la configuración:

| Argumento | Efecto |
|---|---|
| `--repo <ruta>` | Repositorio a analizar. Por defecto, `CodebaseAnalysis:RepositoryPath`, relativo al directorio actual. |
| `--db <ruta>` | BD del grafo. Relativa al repositorio; por defecto `.codebase/codebase.db`. |
| `--output <ruta>` | Carpeta de informes. Relativa al repositorio; por defecto `reports`. |
| `--force-reindex true` | Parte de un grafo nuevo y guarda antes una copia de la ejecución anterior (apartado 3.1). |
| `--reports <lista>` | Informes a ejecutar, separados por comas (alias en el apartado 5). Sin lista se ejecutan los de `RequestedReports`, y si esa lista está vacía, todos. |
| `--log-level <nivel>`, `--debug`, `--trace` | Nivel de log (por defecto `Information`). |

Cualquier clave de configuración admite también la sintaxis estándar de .NET, por ejemplo `--AITaskAgent:Conversation:UseSlidingWindow true`.

El log se escribe en consola y en `<repositorio>/logs/analysis-pipeline-<fecha>.log`; con `--debug` incluye el cuerpo de cada request al modelo.

El primer Ctrl+C cancela el análisis: el pipeline se detiene, el indexador se termina con todo su árbol de procesos, los informes ya escritos se conservan y el proceso sale con código 130. Un segundo Ctrl+C termina el proceso sin esperar.

## 3. Flujo

El pipeline encadena seis steps del framework en cinco fases, porque los dos enriquecedores comparten la fase `enrich`; el quinto step es un `ParallelStep` que lanza un auditor por informe solicitado.

```mermaid
flowchart LR
    S1["1. DetectAndIndexGraphStep"] --> S2a["2a. LanguageEnricherStep<br/>(Java, Struts/JSP)"]
    S2a --> S2["2b. BdpEnricherStep<br/>(fallback: SemanticEnrichmentStep)"]
    S2 --> S3["3. SqlFacetExtractorStep"]
    S3 --> S4["4. ParallelReportsExecution<br/>9 auditores"]
    S4 --> S5["5. ExecutiveSynthesizerStep"]
    S1 -. escribe .-> DB[(".codebase/codebase.db")]
    S2a -. enriquece .-> DB
    S2 -. enriquece .-> DB
    DB -. SQL .-> S3
    S4 -. 01..09 .-> R["reports/"]
    S5 -. 00 .-> R
```

### 3.1 Detección e indexación (`DetectAndIndexGraphStep`)

Con `ForceReindex`, lo primero es mover a `<carpeta de la BD>/backups/<yyyyMMdd_HHmmss>/` la BD (con sus ficheros `-wal`, `-shm` y `-journal`), las carpetas `access_export` de OfficeTools y los diez informes del pipeline, conservando su ruta relativa al repositorio. Los informes se mueven por nombre y no vaciando la carpeta, porque `OutputReportsPath` es configurable y podría contener Markdown ajeno. La copia queda disponible para comparar resultados entre ejecuciones.

Después se indexa con `codebase-memory-mcp cli index_repository` si no hay BD, si se ha forzado o si la BD no contiene nodos de código (tipos como `Class`, `Interface`, `Struct` o `Enum`, funciones y métodos, `CsProject`, `AccessTable` o `AccessQuery`). El indexador escribe en su caché (`~/.cache/codebase-memory-mcp/<proyecto>.db`, con el nombre de proyecto que el propio indexador informa al terminar) y el step copia esa BD a `DatabasePath`. Después retira del grafo los nodos que estén bajo la carpeta de la BD, la de informes o `<repositorio>/.codebase`, porque el indexador recorre también la salida del propio pipeline (informes, copias de `backups/`, documentos subidos desde la web) y la siguiente pasada la auditaba como si fuera código del repositorio. Los nodos que añade el pipeline (Office, Markdown, enriquecimiento por LLM) usan el mismo `project` que los del indexador, cuyo esquema lo exige. A continuación se asegura el esquema (tablas `nodes` y `edges`, columnas duplicadas `file`/`file_path` y `line_start`/`start_line`, índices únicos) y, si el repositorio no tiene ni nodos estructurales ni artefactos Office, el pipeline se detiene: no hay nada que auditar.

Si hay artefactos Office, `IngestOfficeArtifactsStep` (OfficeTools) incorpora al grafo el esquema de Access, el VBA, los formularios con su código y las secciones de los documentos Word. Por último, `WorkflowAndMarkdownEnricher` registra cada `.md` del repositorio como nodo `DocSection`, o `PromptTemplate` si es una plantilla, excluyendo `.git`, `bin`, `obj`, `node_modules`, `.codebase` y la carpeta de informes.

Tras la ingesta Markdown se reincorporan al grafo las fuentes que la web marcó para él en `.codebase/knowledge/graph-sources.json`, porque reindexar sustituye la BD entera y las habría perdido. Los documentos aportados y los informes propios vuelven en este punto, con su contenido actual, para que los auditores los vean; los informes del catálogo marcados se retiran, porque son la salida de la ejecución anterior, y vuelven tras la síntesis ya regenerados. Si el run no llega a la síntesis, porque falla o se cancela antes, `CodebaseAnalysisPipeline` los reincorpora al terminar con el contenido que haya en disco, de modo que no quedan fuera del grafo hasta el siguiente análisis. Cada reincorporación se anuncia en el log («🧩 Reincorporados al grafo …»), y sin fuentes marcadas ninguno de estos pasos escribe ni dice nada.

### 3.2 Enriquecimiento (`LanguageEnricherStep`, `BdpEnricherStep` y `SemanticEnrichmentStep`)

`LanguageEnricherStep` abre la fase. Recorre el repositorio en disco, sin entrar en `.git`, `bin`, `obj`, `node_modules`, `.codebase`, `.gradle`, `.idea`, la carpeta de informes, las salidas `target`, `build` y `out` que están en la raíz o junto a un fichero de build, ni las raíces de test, y deja en el contexto los lenguajes que ha encontrado. La presencia de `.java` activa el analizador Java y la de algún `struts-config*.xml` el plugin Struts/JSP, por este orden; si no hay ninguna de las dos señales, el step se limita a informar de lo detectado. No depende de la marca de grafo enriquecido que usa `BdpEnricherStep`: cada enriquecedor nativo decide por su fila en `enrichment_runs`.

El analizador Java es un único fuente, `Enrichment/Java/JavaAnalyzer.java`, que el `.csproj` de Core copia a la salida y que se ejecuta con el *source launcher* del JDK configurado (`java <JvmOptions> --add-exports … JavaAnalyzer.java --request <petición>`), así que no hay paso de compilación ni binarios. Antes de lanzarlo se comprueba que el fichero `release` del JDK declara la versión 17 o superior, y el classpath se compone con los jars del repositorio más `JavaAnalyzer:ProvidedClasspath`. La petición (`request.txt`), el resultado (`java-analysis.jsonl`) y la salida del proceso (`java-analyzer.log`) quedan en `<carpeta de la BD>/enrichment/java/`, que con la BD por defecto cae dentro de `.codebase/` y no entra en el grafo. El resultado lo aplica .NET sobre la copia `.codebase/codebase.db` en una transacción, sin abrir nunca la BD de `~/.cache/codebase-memory-mcp`: casa tipos y métodos con los nodos del indexador por `qualified_name`, crea como nodos propios las sobrecargas que el indexador funde en uno (con sufijo de tipos en el QN y `overload_of`), completa sus propiedades (firma, tipos completos, accesibilidad, anotaciones, Javadoc decodificado y `cyclomatic`), sustituye las `CALLS`, `INHERITS` e `IMPLEMENTS` del indexador en los ficheros analizados por las resueltas y retira de la copia los nodos del código de test (`testSourceDirectory` del `pom.xml` raíz, `src/test/java` y `JavaAnalyzer:TestRoots`).

El plugin Struts/JSP lee con .NET, sin compilar nada, los `struts-config*.xml`, las definiciones de Tiles y las JSP. Crea un nodo `Route` por acción, con `HANDLES` desde su clase si está en el grafo, un nodo `Jsp` por JSP y uno `TilesDefinition` por definición, con las aristas `FORWARDS_TO`, `SUBMITS_TO` (formularios `html:form`), `INCLUDES`, `RENDERS` y `EXTENDS_DEFINITION`. Una JSP queda marcada como sospechosa si importa algo que casa con `StrutsJsp:SuspiciousImportPatterns` (por defecto DAO, `java.sql` y `javax.sql`) o si su código Java contiene SQL. Los imports de negocio o de servicio (`StrutsJsp:BusinessImportPatterns`) se anotan en `business_imports` y solo la marcan, con el motivo `business-code-in-scriptlet:<import>`, cuando el código de un scriptlet `<% %>` o de una declaración `<%! %>` usa lo importado; importar una utilidad para pintarla en una expresión `<%= %>` no cuenta. Con un import con comodín (`pkg.*`) basta con que un scriptlet use una clase con mayúscula inicial que no venga de otro import ni de `java.lang`, que es una aproximación: sin compilar no se sabe de qué paquete sale cada clase.

Cada pasada deja una fila en la tabla `enrichment_runs` de la copia, con estado `ok`, `failed` o `skipped`, y un enriquecedor se omite, con un mensaje informativo, cuando ya hay una fila `ok` con su misma versión, la misma huella de la indexación (`projects.name|indexed_at`) y la misma huella de configuración. En Java la configuración que cuenta es la codificación por defecto, el classpath compuesto y las raíces de test; en Struts/JSP, la codificación, los dos grupos de patrones y la última pasada `ok` del analizador Java, de modo que una pasada Java nueva hace repetir también el plugin. Para repetir el enriquecimiento basta con reindexar (`ForceReindex` sustituye la copia entera), cambiar alguno de esos valores o borrar las filas de `enrichment_runs` de la copia.

Ningún fallo de estos enriquecedores detiene el pipeline. Sin `JdkPath`, con un JDK que no existe o es anterior al 17, el step emite un aviso («⚠️ Analizador Java: … Se continúa con el grafo de cbm.») y una fila `skipped`; si el proceso falla, supera `JavaAnalyzer:TimeoutSeconds` o el resultado no se puede aplicar, el aviso va con una fila `failed` y el grafo queda como lo dejó el indexador, salvo el código de test: si hay `.java`, sus nodos se retiran igualmente en una transacción aparte (también con `Enabled` a `false`), se informa de cuántos y la fila `skipped` o `failed` los cuenta en `nodes_removed`. Durante la pasada informa de los lenguajes detectados, del JDK, del progreso por fase (como mucho cada 10 % de los ficheros) y, al terminar, de los ficheros analizados, el porcentaje de llamadas resueltas, las aristas sustituidas y creadas, las sobrecargas creadas y los nodos de test retirados, más el desglose por fases de la escritura en el grafo (que también queda en `details.write_timings_ms` de la fila `ok`), con avisos aparte para los paquetes que faltan en el classpath (los diez primeros, con la sugerencia de añadir sus jars en `ProvidedClasspath`) y para los ficheros con errores de compilación. Otro aviso señala una posible deriva de los nombres de cbm: si más del 5 % de los tipos, o de los métodos sin contar las sobrecargas, no casan con un nodo de cbm y se crean como nodos nuevos, la pasada termina `ok` pero avisa de que los nombres de cbm no casan con los del analizador y pregunta si ha cambiado la versión de cbm; las dos proporciones y el umbral quedan en `details.cbm_match` de la fila. Las líneas que escribe el proceso Java van al canal `indexer`, como la salida del indexador.

`BdpEnricherStep` se omite si el grafo ya está enriquecido, lo que se decide por la presencia de nodos `CsProject` o de propiedades `afferent_coupling`, `cyclomatic` o `in_cycle`, sin contar las de los nodos de la ingesta de Office (`origin` `office_tools` o `access_vba_extractor`) ni las del analizador Java, que miden otro código: un `.docx` o un `.accdb` en el repositorio no deja sin Roslyn el código .NET. Tampoco cuentan los nodos que creó el fallback semántico (`origin` `ai_enricher`), así que su salida no marca el grafo como enriquecido y en la siguiente ejecución se vuelve a intentar Roslyn. El fallback semántico tampoco llama al modelo si no encuentra ficheros de rutas, controladores o DI que enviarle, como en un repositorio solo con Access. En caso contrario ejecuta `BdpGraphEnricher.CLI enrich --solution --db --project`, que calcula sobre la solución .NET métricas como complejidad ciclomática, acoplamiento o registros de DI. El código de salida 2 se trata como advertencia y cualquier otro distinto de 0 como error.

Si `LanguageEnricherStep` encontró Java y no C#, `BdpEnricherStep` lo dice en el log y no ejecuta ni el CLI ni el fallback, porque el enriquecimiento de ese repositorio es el del analizador Java; con C#, o sin ninguno de los dos lenguajes, su camino es el de siempre. Cuando el enriquecedor está deshabilitado (`BdpEnricher:Enabled`), no se encuentra o no hay `.sln`/`.slnx` dentro del repositorio, se usa `SemanticEnrichmentStep`, salvo que `BdpEnricher:Required` sea `true`, en cuyo caso el pipeline aborta. Este fallback envía al rol `Enricher` hasta 15 ficheros de entrada (controladores, rutas, `Program`, módulos de DI; 4000 caracteres por fichero) y vuelca en una transacción los nodos, aristas y actualizaciones de propiedades del JSON que devuelve. Las marcas las pone el código y no el modelo: los nodos nuevos llevan `origin: "ai_enricher"`, `enriched_by: ["SemanticEnricherAgent"]` y `enriched_at`, y las aristas y las propiedades que completa en nodos existentes, `enriched_by`. Del modelo solo pasan propiedades semánticas (rutas y verbo, autenticación y roles declarados, contratos, ciclo de vida de DI, método de entrada, asincronía, visibilidad, descripción; `SemanticEnrichmentStep.AllowedNodeProperties` y `AllowedEdgeProperties`); las métricas (`cyclomatic`, `fan_in`, `loc_*`, `afferent_coupling`, `in_cycle`…) y las marcas que proponga se descartan con un aviso que las nombra. Una arista que ya existe no se toca y todo se limita al proyecto del grafo. Como los enriquecedores nativos, el fallback deja su fila en `enrichment_runs` (enriquecedor `SemanticEnricherAgent`, con los nodos creados y completados y las aristas) y no vuelve a llamar al modelo si ya hay una fila `ok` con su versión, la misma huella de la indexación y la misma huella de lo que envía (lenguaje, frameworks y el lote de ficheros): su salida sigue en el grafo aunque no lo marque como enriquecido. Se repite si cbm vuelve a indexar, si cambian esos ficheros o con `ForceReindex`, y entonces, antes de escribir, retira la salida de la pasada anterior. Sin tabla `projects` no hay huella de indexación y se repite siempre. Si la respuesta no es JSON válido, o viene vacía, se registra un aviso y una fila `failed`, y el pipeline sigue con el grafo tal como estaba.

### 3.3 Extracción de facetas (`SqlFacetExtractorStep`)

Los auditores no consultan el grafo para obtener sus datos de partida: un paso determinista ejecuta las consultas SQL de cada informe y deposita el resultado en JSON dentro de `ReportFacetInput`. Así cada auditor arranca con sus datos en el prompt, sin gastar iteraciones de herramientas, y el motor de consultas del indexador no interviene. Cada fila lleva `file`, `start_line` y `end_line`, y en tres facetas (métodos de mayor complejidad, hotspots críticos y ranking de hotspots) se adjunta además el `code_snippet` leído del disco, con un máximo de 10 elementos y 70 líneas por elemento.

Un dato que falta es desconocido y no se presenta como negativo. `ZeroFaninClasses` solo lista tipos con `fan_in` conocido e igual a 0, sin los que atienden una ruta (`HANDLES`) ni los que tienen subtipos; `UnvalidatedRoutes` solo las rutas con `auth_required = false`, y la matriz de seguridad y el resumen de rutas escriben `desconocido` cuando falta el dato. Cada `LIMIT` va con un `ORDER BY` determinista, por la métrica de la faceta y después por nombre, y una consulta que falla llega al auditor como «Faceta no disponible por un error SQL …: no es un conjunto vacío». Cuando faltan las propiedades, las facetas calculan en tablas temporales de la conexión lo que el grafo permite: `fan_in` y `fan_out` de métodos y tipos por aristas `CALLS` resueltas (con `enriched_by` de un enriquecedor que no sea el fallback del LLM, y solo en los nodos que marcó ese mismo enriquecedor; en un tipo no cuentan sus llamadas internas), `method_count` por `DEFINES_METHOD`, `cyclomatic_total` como suma de sus métodos si todos la tienen, y la LOC por el rango de líneas. Cada valor dice de dónde sale en un campo `*_source` (`grafo`, `calculado: aristas CALLS resueltas por JavaAnalyzer`, `calculado: aristas DEFINES_METHOD`…). Con el `fan_in` calculado, `ZeroFaninClasses` pide además que el tipo declare constructor, porque instanciarlo con el implícito no deja arista.

Cuatro facetas llevan a los informes el material Java y Struts/JSP del grafo: `SuspiciousJsps` (JSP marcadas por el plugin, con sus motivos, scriptlets, imports de negocio, SQL y sesión; informes 05, 06 y 08), `StrutsActionsWithoutHandler` (acciones sin `HANDLES`, con el motivo; informes 03 y 07), `UnresolvedForwards` (forwards sin destino, de la última pasada `ok` del plugin en `enrichment_runs`; informes 04 y 05) y `TypeHierarchy` (supertipos por número de subtipos, con cuántas aristas `INHERITS`/`IMPLEMENTS` son resueltas y cuántas heurísticas de cbm; informe 06). Las facetas se serializan sin escapar los caracteres no ASCII.

Una faceta no sale del grafo: `HardcodedSecrets` recorre en disco los ficheros de texto que referencia el grafo y recoge las credenciales escritas como literal (un identificador de tipo `password`, `pwd`, `secret`, `api_key`, `token` o `credential` asignado a una cadena, o un `PWD=` en una cadena de conexión). El valor se enmascara (`Eu*** (8 caracteres)`) y las plantillas prohíben reproducirlo. Existe porque una contraseña en un módulo pequeño, fuera de los hotspots precargados, no aparecía en ningún informe: dependía de que el modelo abriera el fichero. Se descarta el literal cuando el último segmento del identificador (en PascalCase, camelCase o snake_case) nombra una referencia a la credencial y no la credencial, como `Id`, `Name`, `Path`, `File`, `Url`, `Provider`, `Type`, `Length`, `Timeout` o `Version`: así `UserSecretsId` o `token_url` no cuentan, mientras que `ApiKey`, `ClientSecret` o `access_token` sí, porque `Key`, `Secret` y `Token` no están en esa lista. Las plantillas de los informes 05 y 07 permiten además descartar un falso positivo evidente del extractor, dejando constancia del fichero, la línea y el motivo, y ante la duda lo tratan como secreto real.

Otra faceta, `ProvidedDocumentation`, lleva a cada auditor el índice de los documentos subidos desde la web con `useInAnalysis`: hasta 30 y `CodebaseAnalysis:Documents:AnalysisIndexMaxChars` caracteres en total (8000 por defecto), con id, título, familia, títulos de sección, los 600 primeros caracteres del texto extraído y, si el documento está en el grafo, hasta 20 símbolos de código que describe. Cuando hay que recortar, se quita antes el extracto de un documento que el documento entero, y cualquier `@[` del texto se neutraliza porque el renderer de plantillas lo resolvería como include. El bloque entra en todas las plantillas de auditor por `templates/_provided_documentation.md`, con la regla de que es contexto del usuario y no prueba nada sobre el código; sin documentos es `[]`, y el auditor lee el documento completo con `read_document` si lo necesita.

El step también detecta el ecosistema (por extensiones de fichero y etiquetas del grafo) y calcula las métricas globales. Las LOC se cuentan por fichero y se toma lo primero que haya de tres fuentes: el `loc_total` del contenedor del fichero (`Module`, `Form`, `File`); la suma del `loc_total` de sus tipos (`Class`, `Interface`, `Struct`, `Record`, `Enum`, `Trait`), para no contar dos veces un módulo y las clases que contiene; y, cuando el indexador no da `loc_total` (codebase-memory no lo da en C#, y un repositorio C# sumaba 0), el rango de líneas del contenedor o, si no lo hay, la última línea de sus símbolos. Las dos últimas solo se aplican a ficheros con símbolos de código, de modo que Markdown, JSON o YAML no cuentan.

### 3.4 Auditorías en paralelo (`ParallelReportsExecution`)

Cada informe solicitado es un `CustomStatelessTemplateLlmStep<ReportFacetInput, SingleReportResult>` con su rol, su par de plantillas y acceso a `view_file`, `view_code_item`, `graph_search`, `graph_neighbors`, `graph_domain` y `read_document` (`AnalysisPipelineFactory.AuditorToolNames`). Cada auditor tiene un límite de `CodebaseAnalysis:Timeouts:AuditorMinutes` (15 minutos) con sus reintentos, y el conjunto uno de `ReportsMinutes` (60), porque con nueve auditores concurrentes y reintentos los 20 minutos de antes no daban margen. Corren a la vez tantos auditores como procesadores tenga la máquina (lo que hace `Parallel.ForEachAsync` sin opciones), salvo que `CodebaseAnalysis:Reports:MaxParallelAuditors` fije un tope menor; con 0, el valor por defecto, no hay tope propio, porque la decisión de bajarlo espera a medir cuántas llamadas simultáneas aguanta el despliegue. Un valor que no sea un entero mayor o igual que 0 se ignora con aviso.

Cada auditor tiene un tope de iteraciones de herramientas, que es `CodebaseAnalysis:Auditors:MaxToolIterations` (12 por defecto, frente a los 5 del framework) salvo que su rol tenga uno propio en `CodebaseAnalysis:Auditors:MaxToolIterationsByRole`, donde el JSON da 16 a `FlowsAuditor` porque seguir un flujo de extremo a extremo encadena más consultas; un valor que no sea un entero mayor que 0 se ignora con aviso. Agotar el tope ya no hace fallar el informe, que antes terminaba con «Maximum tool iterations (5) exceeded». El framework devuelve ese error tipado como `ToolIterationLimitExceededException`, y el auditor (`CustomStatelessTemplateLlmStep`) lo resuelve en su `SwitchToNextFallback`: repite el step sobre la misma conversación, que aún conserva los resultados reunidos porque el bookmark no se ha restaurado, sin herramientas y con un mensaje que le pide redactar el informe completo con su línea `analysis-meta` y señalar lo que no haya podido verificar. El log lo avisa con «agotó su tope de herramientas … se redacta con lo consultado». Si ese intento falla, o el modelo vuelve a pedir herramientas hasta agotar el tope, falla el informe, y en ese intento no se cambia de proveedor. Un fallo del proveedor, que el framework tipa como `LlmProviderException`, sigue pasando al fallback del rol como antes; es el único error ante el que `BaseLlmStep` cambia de motor. El informe se escribe en disco en cuanto termina su auditor, de modo que sobrevive aunque falle la síntesis. Un resultado con error no se escribe como informe, y una respuesta cortada por `MaxOutputTokens` se avisa en consola. Los auditores corren en `TolerantReportsParallelStep`, que a diferencia del `ParallelStep` del framework no detiene el pipeline cuando falla alguno: la síntesis se ejecuta con los informes disponibles, salvo que hayan fallado todos.

Cada informe termina con una línea de metadatos que el pipeline lee de forma determinista:

```markdown
<!-- analysis-meta: health=Red; critical=6 -->
```

`health` es el semáforo global (`Green`, `Amber`, `Red`); `critical`, que solo emite el informe de errores, es el número de defectos P0 y P1. Si la línea falta, el semáforo queda en `Unknown` y se avisa, en lugar de deducir un color buscando palabras en el texto.

La severidad sigue una rúbrica P0-P3 explícita en `report_errores_prompt.md`, el único informe que la usa: P0 es lo explotable o dañino sin condiciones adicionales, e incluye siempre un secreto real escrito en claro en código o configuración versionada; P1, el impacto grave que necesita una condición más; P2, el fallo acotado; P3, lo latente sin impacto observable hoy. El informe cierra con una matriz de hallazgos con, al menos, las columnas `ID | Severidad | Tipo | Evidencia`. El valor de `critical` no se toma tal cual del modelo, porque no siempre cuadraba con su propia matriz: tras cada auditor, el pipeline cuenta los P0 y P1 de las tablas con columna de severidad (una vez por ID, con `SEC-01` y `SEC-001` como el mismo, e ignorando las tablas dentro de bloques de código) y, si la cifra difiere de la declarada, corrige la línea de metadatos y lo avisa en el log. La corrección se aplica al informe de errores y a cualquier otro que declare `critical`. Antes de escribir un informe o el `00`, se quita también un H1 inicial que solo sea un nombre de fichero `.md` cuando detrás viene el título real.

### 3.5 Síntesis ejecutiva (`ExecutiveSynthesizerStep`)

El rol `ExecutiveSynthesizer` recibe, por cada informe, su semáforo, su resumen y su índice de secciones, junto con las métricas globales, y genera `00_resumen_ejecutivo.md`. Los informes de tipos que no se han ejecutado en esta pasada pero existen en la carpeta de salida se incorporan marcados como de una ejecución anterior; sin esto, una ejecución parcial (`--reports di`) producía un resumen basado en un solo informe que contradecía a los demás. Un informe cuyo auditor ha fallado figura con el motivo del error, como no generado o, si hay una versión anterior en disco, como de una ejecución anterior. Los defectos críticos proceden de la línea `critical` del informe de errores y, si no hay dato, figuran como "no disponible" en vez de como cero. Si el modelo no devuelve contenido, se escribe un resumen de respaldo construido sin LLM.

### 3.6 Límites de tiempo

Todos los límites del análisis salen de `CodebaseAnalysis:Timeouts` (apartado 4), en minutos, y en todos 0 quita el límite. El del pipeline entero, `PipelineMinutes` (240), lo aplica `CodebaseAnalysisPipeline` con su propio token, y al motor le pasa `Timeout.InfiniteTimeSpan` como `pipelineTimeout` para que no aplique el suyo. Así distingue el timeout de una cancelación del usuario por el token que ha saltado, y un análisis o una regeneración que lo supera termina con el error «El análisis superó el límite de N min (CodebaseAnalysis:Timeouts:PipelineMinutes); súbelo o pon 0 para quitarlo.», que también sale en el log con nivel de error en el momento del corte, en lugar del «A task was canceled.» que daba el motor. Sin él mandaba el timeout global del framework, `AITaskAgent:Timeouts:DefaultPipelineTimeout`, que son 10 minutos y que usan también el chat y los demás pipelines: con él, un auditor que esperaba al modelo se cortaba a los 600 s del arranque con una excepción que la tolerancia de `TolerantReportsParallelStep` no llegaba a ver, y la ejecución terminaba sin resumen ejecutivo. Ese valor global no se toca. Los límites de paso son `DetectMinutes` (15) para `DetectAndIndexGraphStep`, `EnrichMinutes` (20) para `BdpEnricherStep`, `ReportsMinutes` y `AuditorMinutes` (apartado 3.4) y `SynthesisMinutes` (15) para `ExecutiveSynthesizerStep`. El analizador Java conserva los suyos en `JavaAnalyzer` (apartado 3.2), y las facetas y la preparación de una regeneración tienen 5 minutos fijos.

Por debajo de los límites de paso, cada llamada al modelo tiene los suyos en el proveedor (`OpenAILLmService`). Sin streaming, cada intento tiene un plazo de `RequestTimeoutSeconds` (600 s por defecto): un intento sin respuesta en ese tiempo se abandona como fallo reintentable y el reintento sigue su curso, en lugar de esperar los 30 minutos fijos que tenía antes el cliente HTTP. Con streaming, el plazo es de inactividad, `StreamingInactivityTimeoutSeconds` (120 s por defecto): cuenta la espera de la respuesta y de cada línea del stream, se reinicia con cada una y no corta una respuesta larga que sigue llegando. Los dos se fijan en el proveedor (`LlmConfiguration:Providers:<p>:Inference:*`) o en el rol (`LlmConfiguration:Roles:<r>:*`), que manda, y con 0 se quitan. El error nombra la clave, por ejemplo «The request to model 'gpt-5.4' got no response within the per-attempt limit of 600 s (RequestTimeoutSeconds); raise it or set 0 to remove it.», y una cancelación del usuario sigue siendo una cancelación. Con los valores por defecto, un intento colgado consume 10 de los 15 minutos de `AuditorMinutes`, así que al reintento le quedan 5; para que quepan dos reintentos completos hay que bajar `RequestTimeoutSeconds` o subir `AuditorMinutes`. Con Azure y `gpt-5.4` en streaming, la respuesta llega entera al final (apartado 7), así que una respuesta que tarde más de 120 s en generarse corta por inactividad: el chat, que es el único rol con streaming, necesita entonces subir `StreamingInactivityTimeoutSeconds` en su rol.

Sin límite se traduce a `Timeout.InfiniteTimeSpan` y no a null, porque con null el framework aplica su timeout por defecto, de paso o de pipeline. Un valor por encima de lo que admite `CancellationTokenSource.CancelAfter` (unos 49 días, 71582 minutos) se trata también como sin límite en lugar de hacer fallar el paso al arrancar.

### 3.7 Regeneración de informes

`AnalysisRunner.RegenerateAsync` vuelve a generar uno o varios informes sobre el grafo que ya existe, sin repetir el resto del análisis. Ejecuta un pipeline reducido (`AnalysisPipelineFactory.CreateRegenerationPipeline`, que en los eventos se llama `CodebaseAnalysisRegeneration`): `PrepareRegenerationStep`, `SqlFacetExtractorStep`, los auditores pedidos en `TolerantReportsParallelStep` y, si se pide, `ExecutiveSynthesizerStep`. No detecta, no indexa, no ingiere Office ni Markdown y no enriquece, así que los informes regenerados se basan en el grafo de ahora, que puede no ser el de la ejecución original. Las facetas se recalculan porque solo viven en memoria y son consultas SQL de segundos.

`PrepareRegenerationStep` va en la fase `facets` y deja en el contexto las mismas claves que la detección. Si no existe la BD o no tiene grafo estructural, falla con un mensaje que pide lanzar un análisis completo. Si existe, asegura el esquema y retira del grafo los informes del catálogo marcados, con el mismo código que la detección, para que vuelvan con el contenido nuevo en la síntesis o, si no se llega a ella, en el `finally` de `CodebaseAnalysisPipeline`. Cada auditor escribe su informe en `reports/` al terminar, como en el análisis completo, y la síntesis toma de disco los informes que no se han regenerado. Los demás ficheros no se tocan, y sin síntesis tampoco el `00`. La CLI no ofrece la regeneración: la usa la web, que la describe en su README.

## 6. Herramientas

A los auditores se les asignan `view_file`, `view_code_item`, `graph_search`, `graph_neighbors`, `graph_domain` y `read_document`. El sandbox de FileTools se fija en la raíz del repositorio analizado, y todas son de solo lectura. Las que leen ficheros (`view_file`, `grep_search`, `view_code_item`, el código de `graph_search` con `include_code`), el escáner de secretos y los fragmentos de las facetas decodifican cada fichero con la regla del analizador: UTF-8 si lo es y, si no, la codificación que declare el repositorio (`JavaAnalyzer:DefaultEncoding` o el `pom.xml`) o Latin-1. Antes lo leían todo como UTF-8, y en un repositorio ISO-8859-1 cada tilde salía como U+FFFD y un `grep_search` con acentos no encontraba nada. `grep_search` no usa ripgrep sino expresiones regulares de .NET sobre el texto ya decodificado, así que no tiene la limitación de `--encoding`. El programa registra además `graph_map`, `graph_health`, `graph_flows`, las de OfficeTools (`access_schema`, `access_query_sql`, `docx_search`) y las dos que lee el chat de la web sobre los informes (`list_reports`, `read_report`), pero ningún auditor las tiene asignadas, porque ninguna plantilla las usa. El chat de la web usa también `graph_domain` y `graph_neighbors` (vecinos de un nodo por `CALLS`, `INHERITS`, `IMPLEMENTS`, `DEFINES_METHOD`, `HANDLES` y las aristas Struts/JSP); `graph_map`, `graph_health` y `graph_flows` están disponibles para quien construya otros steps. `graph_neighbors` dice la procedencia de cada arista en su columna `Procedencia`: `resuelta · <enriquecedor>` si lleva `enriched_by`, `estimada por LLM` si solo la marcó el fallback semántico, `heurística cbm` (con su `strategy` y su `confianza` cuando cbm las da) si no lleva marca, y `estructura cbm` para la pertenencia (`DEFINES_METHOD`, `DEFINES`, `CONTAINS_*`, `MEMBER_OF`). La cabecera cuenta todas las aristas pedidas por procedencia y, si alguna no está resuelta, avisa de que son pistas que hay que confirmar en el código. `graph_search` devuelve, además de la tabla de nodos, sus propiedades útiles (firma, tipos, jerarquía, rutas de framework, indicadores de JSP, docstring), salvo con `include_properties: false`. La conexión al servidor MCP de `codebase-memory-mcp` está desactivada por defecto (`ConnectMcp: false`), porque sus herramientas duplican `graph_search` y las demás `graph_*`; el ejecutable se sigue usando como indexador en el paso 1.

## 7. Limitaciones conocidas

Las plantillas y la configuración no contienen nada propio de un repositorio concreto: los ejemplos son genéricos y las rutas se resuelven contra el repositorio analizado o contra las ubicaciones de instalación por defecto. Lo que sigue son límites del propio pipeline.

- **Dependencia del indexador:** las facetas se basan en labels y propiedades concretas (`DiRegistration`, `Route`, `cyclomatic`, `fan_in`, `hotspot`…) que solo generan algunos indexadores. En un lenguaje cuyo indexador no las produce, esas facetas llegan vacías y el auditor debe declararlas no evaluables; `fan_in`, `fan_out`, `method_count`, `cyclomatic_total` y la LOC se calculan del grafo cuando hay aristas con que hacerlo, pero `hotspot`, `in_cycle`, `instability` o `auth_required` no. `CreationalCandidates` busca por nombre para cubrir en parte este hueco en DI.
- **Puntos ciegos del `fan_in` calculado:** cuenta llamadas a métodos y constructores por `CALLS` resueltas; no ve referencias de tipo, campos estáticos, reflexión ni el uso desde JSP, XML de framework o `web.xml`. Por eso `ZeroFaninClasses` son candidatos y la regla del grafo obliga a cruzarlos antes de llamarlos código muerto.
- **Un auditor que falla deja un hueco:** `TolerantReportsParallelStep` deja seguir a la síntesis, que declara el informe como no generado (o usa el de una ejecución anterior si sigue en disco) y el proceso termina con código 1. Si fallan todos, el pipeline se detiene.
- **Uso de herramientas a criterio del modelo:** con las facetas en el prompt, los auditores recurren poco a `view_file`; los hallazgos fuera de los hotspots precargados dependen de que el modelo decida leer más código.
- **Proveedores soportados:** solo los servicios del proyecto `OpenAILLmService` (`azure-openai`, `openai`, `openrouter`); otro `ServiceType` detiene el arranque.
- **Cumplimiento de las reglas de redacción:** dependen del modelo y no son absolutas. En la ejecución de referencia quedan 3 contrastes "no X, sino Y" y 1 gerundio final en unas 29000 palabras, frente a 16 y 13 antes de las reglas.
- **Detección de secretos por patrón:** `HardcodedSecrets` solo reconoce literales asignados a identificadores con nombre de credencial y claves `PWD`/`Password` de cadenas de conexión. Un secreto guardado en una variable con otro nombre, cifrado o partido en varias cadenas no se detecta, y tampoco uno asignado a un identificador cuyo último segmento sea de referencia (`SecretVersion`, `PasswordHint`), que el filtro de falsos positivos descarta.
- **Alcance del enriquecimiento Java:** el Java de los scriptlets de las JSP no se compila, así que sus llamadas no forman parte del grafo resuelto; las declaraciones dentro de clases anónimas o locales no se emiten y sus llamadas se atribuyen al método que las contiene. La tabla `nodes_fts` conserva las filas de los nodos de test retirados; la aplicación no la consulta.
- **LOC aproximadas sin `loc_total`:** cuando el indexador no da `loc_total`, como en C#, las LOC de un fichero salen de su rango de líneas, así que cuentan líneas físicas, con comentarios y líneas en blanco.
- **`critical` depende de la matriz:** la corrección determinista solo actúa si el informe tiene una tabla con columna de severidad; sin ella se conserva la cifra que declara el modelo. El aviso de corrección solo está probado por tests, porque en las ejecuciones reales el modelo ya cuadraba la cifra.
